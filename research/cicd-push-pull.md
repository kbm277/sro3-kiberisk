# Исследование. CI/CD: push-модель и pull-модель

В задании вторая схема иногда называется pool model. Ниже она разобрана как **pull-модель**: агент внутри среды сам забирает изменения. Это пара к push-модели. Общий пул раннеров GitLab — другая тема, к способу выкладки она не относится.

CI/CD здесь значит одно: после коммита код проверяется и попадает в работающую среду без ручного копирования файлов. Модели различаются тем, **кто открывает соединение и у кого лежит право менять среду**.

## 1. Push-модель

Пайплайн сам доставляет результат. Раннер собирает артефакт и по сети подключается туда, куда нужно выложить: к Docker Hub, по SSH на сервер, к API Kubernetes.

Как это идёт:

1. Разработчик пушит ветку в Git.
2. CI запускает сборку и тесты.
3. Тот же пайплайн логинится во внешнюю систему токеном из переменных CI.
4. Пайплайн отправляет образ, файлы или манифест.
5. Успех или ошибка видны в логе этой же задачи.

```text
Git → раннер CI → (токен, исходящее соединение) → Hub / сервер / кластер
```

В этом репозитории так устроен `.gitlab-ci.yml`. Задача `push` на ветке `main` делает `docker login` и `docker compose push`. Раннер сам отправляет пять образов на Docker Hub. Кластер или сервер в этой схеме ничего не опрашивает.

Плюсы:

- Вся цепочка видна в одном пайплайне: сборка и выкладка заканчиваются вместе.
- Для одного стенда, одного сервера или загрузки образов в registry хватает файла CI, без отдельного агента в среде.
- Откат и повторный запуск делаются кнопкой перезапуска задачи.
- Студенческий и небольшой проект поднимается за один вечер.

Минусы:

- У CI должен быть секрет с правом записи в среду. Украденный `DOCKERHUB_TOKEN`, kubeconfig или SSH-ключ равен доступу к выкладке.
- Раннер обязан достучаться до среды. Для закрытого контура в файрволе открывают вход снаружи.
- Секрет легко попадает в лог, если команда печатает переменные. В реестре рисков этого стенда это отдельная строка: «токен Hub попал в лог CI».
- Ручное изменение сервера пайплайн не замечает: в Git одно состояние, на машине другое.
- Один и тот же деплой в несколько кластеров размножает токены и сетевые правила.

## 2. Pull-модель

Среда сама забирает желаемое состояние. CI только проверяет код и обновляет Git или тег образа. Внутри кластера работает контроллер (Argo CD, Flux). Он по расписанию читает репозиторий и приводит кластер к тому, что записано в Git.

Как это идёт:

1. Разработчик пушит коммит. CI собирает образ и кладёт его в registry.
2. В Git обновляется тег образа или манифест. Это делает человек через merge или отдельный коммит пайплайна в репозиторий конфигурации.
3. Контроллер в кластере по исходящему соединению читает Git.
4. Если кластер отличается от Git, контроллер применяет разницу.
5. Статус выкладки смотрят в контроллере, не только в зелёной задаче CI.

```text
Git ← (исходящее соединение, секрет внутри кластера) ← контроллер в среде
CI → только сборка и публикация образа в registry
```

Плюсы:

- У пайплайна нет права менять кластер. Компрометация раннера не даёт прямой выкладки в прод.
- Кластеру достаточно исходящего доступа. Вход из интернета к API Kubernetes для CI не открывают.
- Git становится журналом того, что должно работать. Откат — это revert коммита, дрейф сервера контроллер показывает сам.
- Несколько кластеров читают один репозиторий и не требуют отдельного токена на каждый деплой из CI.

Минусы:

- Появляется ещё один привилегированный компонент. Контроллер сам по себе цель: его права в кластере широкие.
- Защищать нужно уже не только токен CI, а ветку, которую контроллер читает. Merge в неё равен выкладке.
- Результат не заканчивается на зелёном пайплайне. Синхронизация идёт с задержкой, ошибку смотрят в Argo CD или Flux.
- Для одного контейнера и `docker compose` на учебной машине это лишняя сложность.

## Сравнение

| | Push | Pull |
| --- | --- | --- |
| Кто начинает выкладку | Раннер CI | Агент внутри среды |
| Где секрет с правом менять среду | В переменных CI | Внутри среды |
| Направление соединения | CI → среда | Среда → Git и registry |
| Где виден итог | Лог задачи CI | Контроллер и Git |
| Дрейф «на сервере поправили руками» | Не виден | Виден, агент возвращает состояние из Git |
| Порог входа | Низкий | Нужен Kubernetes или отдельный агент |

## Когда что использовать

**Push — этот репозиторий и похожие стенды.** Одна команда Compose, образы уходят на Docker Hub, отдельного кластера нет. Пайплайн в `.gitlab-ci.yml` как раз push: раннер сам вызывает `docker compose push`. Так же разумно деплоить одну виртуальную машину по SSH, если сред мало и секрет CI ограничен одной средой, хранится как masked-переменная и не печатается в лог.

**Pull — когда сред несколько и цена ошибки выше.** Kubernetes, отдельные dev, stage и prod, требование откатывать выкладку через Git и не хранить kubeconfig в CI. Тогда CI публикует только образ, а Argo CD или Flux в каждом кластере забирают манифест. Ветку, за которой следит контроллер, защищают так же, как прод: review, запрет прямого push.

**Обычная рабочая схема — обе сразу, на разных шагах.** Push отвечает за доставку артефакта: `docker compose push` в registry. Pull отвечает за применение: сервер или кластер сам делает `docker compose pull` или синхронизацию из Git. Секрет Hub с правом push остаётся в CI. Секрет с правом менять работающие контейнеры в CI не кладут.

Для киберриска выбор модели — это выбор, где окажется секрет и кто сможет им воспользоваться. На учебном стенде из пяти контейнеров достаточен push в Docker Hub. Как только выкладка идёт в несколько закрытых сред, секрет из CI убирают и оставляют среде самой забирать уже собранный образ.

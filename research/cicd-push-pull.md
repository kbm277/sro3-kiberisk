# CI/CD зерттеу

Тапсырмадағы *Pool model* атауын Push моделінің жұбы ретінде **Pull model** деп түсіндіремін. CI (үздіксіз интеграция) код өзгерістерін құрастырып, автоматты түрде тексеруге көмектеседі. CD тексерілген нұсқаны жеткізуге және орналастыруға қатысты. Push пен Pull модельдері орналастыруды кім бастайтыны және ортаға өзгеріс енгізу құқығы кімде болатыны бойынша ажыратылады. [OpenGitOps қағидалары](https://opengitops.dev/).

## 1. Push моделі

**Қалай жұмыс істейді?** Код өзгергенде CI тесттерді орындайды, контейнер бейнесін құрастырып, тізілімге жариялайды. Содан кейін пайплайн тапсырмасын орындайтын раннер мақсатты серверге SSH арқылы немесе платформа API-і арқылы қосылады. Ол жаңа нұсқаны қолданады және қызметтің іске қосылғанын тексереді.

**Мысал.** Бір сынақ сервері бар командада GitLab раннері серверге SSH арқылы қосылып, бекітілген контейнер бейнесін жүктеу және Docker Compose арқылы қызметті жаңарту командаларын іске қосады. Орналастыруды раннер бастағандықтан, бұл Push моделіне жатады. [Орналастыру тапсырмаларын басқару](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/control-deployments).

**Артықшылықтары**

- Бір сервері бар қарапайым жобада бөлек контроллер орнатпай, орналастыруды пайплайнға қосуға болады.
- Тексеру, мақұлдау, орналастыру және нәтижені тексеру бір пайплайнда көрінеді.
- Мақұлданғаннан кейін пайплайн орналастыруды бірден бастай алады.

**Кемшіліктері және кибертәуекелдері**

- Орналастыру тапсырмасы бұзылса, шабуылдаушы оның құқықтары шегінде ортаға өзгеріс енгізе алады. Құрастыру мен орналастыру құқықтарын бөліп, әр ортаға ең аз қажетті рұқсат беру және мүмкіндік болса, OIDC арқылы қысқа мерзімді тіркелгі деректерін қолдану керек.
- Раннер серверге немесе API-ге желі арқылы жете алуы тиіс. Жабық ортада ішкі желіге орналастырылған арнайы раннерді пайдалануға болады.
- Бір реттік орналастырудан кейін ортада қолмен жасалған өзгерістерді анықтау үшін бөлек тексеріс керек.
- Кері қайтару үшін бұрынғы тексерілген артефактіні көрсетіп, қайта орналастыру қажет. Тапсырманы жай ғана қайталау ақаулы нұсқаны қайта орнатуы мүмкін.

[OIDC арқылы қысқа мерзімді қолжетімділік](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws). [GitLab CI/CD айнымалыларын қорғау](https://docs.gitlab.com/ci/variables/).

## 2. Pull моделі

**Қалай жұмыс істейді?** Орналастыруды мақсатты ортадағы немесе оған жақын басқару контурындағы агент бастайды. GitOps тәсілінде репозиторийде қалаулы күй сипатталады. Мысалы, контейнер бейнесінің нұсқасы мен жұмыс істеуге тиіс көшірмелер саны көрсетіледі.

1. CI кодты тексереді, контейнер бейнесін құрастырады және тізілімге жариялайды.
2. Конфигурация репозиторийіндегі манифест жаңа бейненің мазмұн идентификаторына (digest) жаңартылады. Өндірістік орта үшін өзгеріс қорғалған тармаққа тексеру мен мақұлдаудан кейін біріктіріледі.
3. Argo CD немесе Flux сияқты контроллер Git-тен қалаулы күйді оқып, оны нақты күймен салыстырады. Айырмашылық болса, контроллер бапталған саясатқа сай өзгерісті қолданады, ал кластер түйіндері бейнені тізілімнен жүктейді.
4. Команда контроллерден синхрондау күйін, нақты қолданылған Git нұсқасын және қолданбаның жұмысқа қабілеттілігін тексереді.

[OpenGitOps қағидалары](https://opengitops.dev/). [Argo CD автоматты синхрондауы](https://argo-cd.readthedocs.io/en/stable/user-guide/auto_sync/). [Flux күйді салыстыру механизмі](https://fluxcd.io/flux/components/kustomize/kustomizations/).

**Артықшылықтары**

- CI-ге кластерді тікелей өзгерту құқығын берудің қажеті жоқ. Контроллер Git-ке, ал кластер бейне тізіліміне қосыла алса, CI үшін жабық кластердің API-ін ашу қажет болмайды.
- Git тарихынан қандай конфигурация мақұлданғанын көруге болады. Қате нұсқаны кері қайтару үшін алдыңғы қалаулы күйді Git-те қалпына келтіруге болады.
- Контроллер нақты күйдің Git-тегі күйден ауытқуын байқайды. Argo CD-де қолмен жасалған өзгерістерді автоматты түзету үшін `selfHeal` бөлек бапталады.

**Кемшіліктері және кибертәуекелдері**

- Контроллерді орнату, жаңарту және бақылау қажет. Оның тіркелгісі бұзылса, шабуылдаушы контроллер басқаратын ресурстарды өзгерте алады. Рұқсаттарды орта, аттар кеңістігі және ресурс түрлері бойынша шектеу керек.
- Бақыланатын Git тармағындағы рұқсатсыз өзгеріс жұмыс ортасына таралуы мүмкін. Қорғалған тармақ, міндетті код шолуы және бейнені digest арқылы бекіту конфигурация мен артефактіні алмастыру тәуекелін азайтады.
- Git, тізілім немесе контроллер қолжетімсіз болса, жаңа нұсқаны қолдану кешігеді. Пайплайн сәтті аяқталғаннан кейін синхрондау күйін бөлек бақылау қажет.
- Қате конфигурация бірнеше ортаға таралуы мүмкін. Оны алдымен сынақ ортасында тексеріп, өндірістік ортаға кезең-кезеңімен енгізген жөн.

[Argo CD жобалары мен рұқсат шектеулері](https://argo-cd.readthedocs.io/en/stable/user-guide/projects/). [Kubernetes RBAC тәжірибелері](https://kubernetes.io/docs/concepts/security/rbac-good-practices/).

## 3. Салыстыру

| Өлшем | Push | Pull |
| --- | --- | --- |
| Орналастыруды кім бастайды? | CI/CD пайплайны | Агент немесе GitOps контроллері |
| Ортаға өзгеріс енгізу құқығы кімде? | Орналастыру тапсырмасының тіркелгісінде | Агенттің немесе контроллердің тіркелгісінде |
| Негізгі желілік байланыс | Раннер → сервер немесе API | Контроллер → Git, кластер → бейне тізілімі |
| Нәтиже қайда көрінеді? | Пайплайндағы орналастыру және қызметті тексеру нәтижелерінде | Контроллердегі синхрондау және қызмет күйінде |
| Қолмен жасалған өзгеріс қалай анықталады? | Бөлек тексеріс арқылы | Контроллер арқылы, баптауға қарай түзетіледі |
| Қате нұсқа қалай кері қайтарылады? | Бұрынғы артефактіні қайта орналастыру | Git-те бұрынғы күйді қалпына келтіріп, синхрондау |

Екі модельде де дерекқор миграциясы мен деректерді қалпына келтіру бөлек жоспарланады. Қолданбаның алдыңғы бейнесін орналастыру дерекқордағы өзгерістерді өздігінен кері қайтармайды.

## 4. Қай модельді қайда қолданған дұрыс?

| Жағдай | Ұсыныс | Негіздеме |
| --- | --- | --- |
| Бір оқу стенді немесе бір сынақ сервері | **Push** | Пайплайнға бір орналастыру тапсырмасын қосу оңай. Раннердің рұқсатын сол ортаға шектеуге болады. |
| Жабық Kubernetes кластері немесе бірнеше орта мен кластер | **Pull** | CI-ге кластерді тікелей өзгерту құқығын бермей, Git арқылы өзгерістерді мақұлдап, әр ортаның күйін бақылауға болады. |
| CI бейне құрастырады, ал өндірістік орта бөлек басқарылады | **Аралас тәсіл** | CI бейнені тізілімге жібереді. Өндірістік ортадағы контроллер мақұлданған нұсқаны Git-тен оқып, өзі орналастырады. |

## 5. Осы репозиторийге ұсыныс

Жобаның GitLab пайплайны Docker Compose арқылы бес қызметтің бейнесін құрастырып, `docker compose push` командасымен Docker Hub-қа жариялауға арналған. Бұл — артефактіні тізілімге жіберу. Серверде жаңа контейнерлерді іске қосу — бөлек орналастыру қадамы. `docker compose pull` командасы бейнені жүктейді, ал контейнерлерді жаңарту үшін `docker compose up` сияқты бөлек команда қажет. [Жобаның CI конфигурациясы](https://github.com/kbm277/sro3-kiberisk/blob/main/.gitlab-ci.yml). [Docker Compose Push](https://docs.docker.com/reference/cli/docker/compose/push/). [Docker Compose Pull](https://docs.docker.com/reference/cli/docker/compose/pull/).

Оқу стенді үшін Docker Hub-қа жариялау жеткілікті. Жариялау токенінің құқықтарын қажет репозиторийлермен шектеп, GitLab-та қорғалған және бүркемеленген айнымалы ретінде сақтау керек. Пайплайн файлына енгізілетін өзгерістерді де тексерген жөн, өйткені бүркемелеу зиянды скрипттің токенді сыртқа жіберуіне кедергі болмайды. Кейін бір сынақ серверіне автоматты орналастыру қажет болса, Push тапсырмасын қосуға болады. Жоба жабық Kubernetes ортасына көшсе, CI бейнені жариялайды, ал Pull арқылы орналастыруды Argo CD немесе Flux атқарады. [GitLab құпия айнымалыларын қорғау](https://docs.gitlab.com/ci/variables/). [Argo CD автоматты синхрондауы](https://argo-cd.readthedocs.io/en/stable/user-guide/auto_sync/).

**Пайплайнды іске қосқанда ескерілетін жайт.** Қазіргі конфигурацияда құрастыру мен жариялау бөлек Docker-in-Docker тапсырмаларында орындалады. Әр тапсырманың Docker ортасы оқшауланғандықтан, құрастырылған бейнелер жариялау тапсырмасына автоматты түрде өтпейді. Жариялауды іске қосу қажет болса, бейнелерді екі тапсырма арасында тасымалдау немесе құрастыру мен жариялауды бір тапсырмада орындау керек. [GitLab Docker-in-Docker құжаттамасы](https://docs.gitlab.com/ci/docker/using_docker_build/).
